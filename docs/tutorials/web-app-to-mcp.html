CHAPTER 01

Start with the application you already have

TeamBeacon already knows how to calculate delivery metrics. The integration adds a way for an agent to discover and request those metrics, then a small interface for people to inspect them inside a compatible chat host.

EXISTING

Web app

A React + Vite frontend and a Python HTTP API. The API owns metric calculations, persistence, and ingestion.

ADDED

MCP server

A separate Python process that translates two named read operations into a fixed API request.

ADDED

MCP App

A bundled React dashboard that a supporting host can render alongside the conversation.

This walkthrough assumes you can run a local web app and have seen a JSON API. No previous MCP experience is needed. Follow the chapters in order, or jump to the setup recipe if you want to run this checkout first.

Scope of this journey: read insights only. The final widget shows work-stream progress, created/completed flow, net intake, current work in progress (WIP), filters, and source freshness. The data tools still return the richer dashboard envelope. No sync, edits, deletes, or AI-refresh tool was added.

A guide to this working tree

This is based on the uncommitted TeamBeacon implementation reviewed on 9 October 2026, including newly added files that do not appear in a plain git diff. Code excerpts are drawn from this checkout; synthetic examples are labeled. It is a reproducible local integration, not a promise that every agent host renders interactive apps.

CHAPTER 02

Learn the vocabulary through this dashboard

ConceptWhat it means hereConcrete example
HostThe agent application coordinating the model, permissions, tools, and display.Codex or another compatible agent application.
MCP clientThe host-side component that exchanges protocol messages with this server.Launches the Python command and lists its tools.
MCP serverA program publishing a discoverable, typed interface.services.mcp; “server” does not require a web port.
ToolA named operation with described input and output.get_team_dashboard(flow_weeks=4).
ResourceContent identified by a URI that the client can read.Workspace context, metric definitions, or the widget’s HTML.
PromptA reusable interaction template exposed by a server.Optional; this server registers none. Your chat message is not an MCP prompt resource.
TransportThe channel carrying protocol messages.Standard input/output between the local host and Python process.
MCP AppThe optional UI extension: a tool-associated HTML resource and a host bridge.A React work-stream dashboard in a sandboxed frame.

MCP stands for Model Context Protocol. The model can select an available tool; the host’s client carries out the protocol call. MCP itself is neither a language model nor a replacement for the application API. The adapter makes no model call and needs no additional model API key.

Tools, resources, and prompts serve different purposes; defining a resource does not ensure that every host automatically places it into the model’s context. The host chooses how discovery and resource use are surfaced. See the versioned tool, resource, and prompt references.

Three connections, three jobs

Host ↔ MCP server

stdio carries MCP JSON-RPC messages. There is no MCP HTTP endpoint in this implementation.

MCP server ↔ API

HTTP GET requests existing analytics. This is ordinary application HTTP, not MCP transport.

Widget ↔ host

postMessage carries MCP Apps messages. The host relays permitted tool calls.

Two protocol versions, plus an SDK version

The dependency lock pins mcp==1.30.0. Its installed core protocol constant is 2025-11-25; the SDK handles initialization and version negotiation. The widget separately requests MCP Apps 2026-01-26. These dates identify different protocols. Newer core specifications exist; the sequences here intentionally describe the pinned checkout, not every future SDK.

CHAPTER 03

Choose one useful API operation

Start with a question someone already asks: “How are our work streams progressing?” TeamBeacon has an aggregate endpoint that answers it without reconstructing metrics in the frontend.

Existing endpoint
GET /api/team/dashboard?flowWeeks=4&recentLimit=5&timezone=Australia%2FMelbourne

The response combines progress, flow, release health, sprint cycle time, and issue details. A workStreams entry includes created/completed counts, net intake, current WIP, and scope completion. The server adds calculation time and source freshness.

Why use an adapter instead of exposing every route?

The web API also has configuration, sync, and refresh operations. A focused adapter provides only the operations this conversation needs. It can rename parameters for a stable public contract, validate inputs, bound output, and explain metric meaning without duplicating calculations.

Agent inputHTTP parameterRule in this implementation
flow_weeksflowWeeks1, 4, or 12; default 4. Monday-based windows include the current partial week.
recent_limitrecentLimitInteger 1–20; default 5. Applies to issue lists, not work-stream rows.
timezonetimezoneValid IANA timezone. Defaults to server configuration.
cycle_time_status_keyscycleTimeStatusMode + repeated cycleTimeStatusOmitted/null: backend defaults. Empty array: explicitly no statuses. At most 50 normalized keys.

Read the entire call path. The original freshness lookup went through a sync-status method that could reconcile interrupted sync runs. This change adds get_jira_data_as_of(), which reads the checkpoint timestamp without running that sync-state recovery. HTTP GET and read-only annotations alone do not establish freedom from side effects; inspect the implementation.

CHAPTER 04

Give the agent a bounded contract

A JSON Schema is a machine-readable contract between a caller and your code: which arguments are allowed, their types, and what a result contains. TeamBeacon uses Python type hints and Pydantic models; FastMCP derives the published schemas from them.

Contract excerpt · imports and validators omitted
class DashboardQuery(PublicModel):
    flow_weeks: Literal[1, 4, 12] = 4
    recent_limit: Annotated[int, Field(strict=True, ge=1, le=20)] = 5
    timezone: str = "Australia/Melbourne"
    cycle_time_status_keys: Annotated[list[str], Field(max_length=50)] | None = None

class DashboardResult(PublicModel):
    schemaVersion: Literal["1"] = "1"
    appliedFilters: DashboardQuery
    uiUrl: str
    warnings: list[str]
    dashboard: Dashboard

PublicModel drops unrecognized fields and rejects non-finite numbers. Additional validators check the timezone, normalize status names, and reject unsafe issue URLs. Returning appliedFilters lets the UI show the scope the server actually used.

The result is data first

The SDK exposes the typed result as structuredContent and also provides a text representation. The widget reads structuredContent; the model can reason about the same result. schemaVersion is our application envelope version, independent of either protocol version.

Synthetic result excerpt · fields omitted for readability
{
  "schemaVersion": "1",
  "appliedFilters": {
    "flow_weeks": 4, "recent_limit": 5,
    "timezone": "Australia/Melbourne", "cycle_time_status_keys": null
  },
  "uiUrl": "http://127.0.0.1:5174",
  "warnings": [],
  "dashboard": {
    "source": "local",
    "generatedAt": "2026-10-09T00:00:00Z",
    "dataAsOf": "2026-10-08T23:00:00Z",
    "workStreams": [{
      "id": 1, "name": "Platform", "completionPercent": 65,
      "newCount": 12, "completedCount": 15, "netFlow": -3,
      "currentWipCount": 4
    }]
  }
}

Calculation time

generatedAt: when the local analytics were calculated. A cache may reuse this result.

Source freshness

dataAsOf: the source checkpoint timestamp, when known. It does not mean every source item changed then.

The client caps upstream data at 512,000 bytes, keeps at most 50 work streams, and trims issue details to recent_limit while preserving counts. Failures become short operational errors. An unavailable metric is not silently converted to zero.

CHAPTER 05

Publish tools and resources

This uses FastMCP from the official mcp.server.fastmcp Python SDK module. The server factory creates one dashboard() function that validates inputs and calls DashboardClient.read(). It registers that same function under two names:

DATA

get_team_dashboard

Use for questions and summaries. It returns facts without requesting a widget.

DISPLAY

show_teambeacon_dashboard

Use for visual inspection. It returns the same facts and associates the tool with an HTML resource.

Both operations fetch authoritative API data themselves. This implementation does not ask the model to fabricate dashboard values or pass a prepared dashboard into the render tool.

Tool annotations
READ_ONLY = ToolAnnotations(
    readOnlyHint=True,
    destructiveHint=False,
    idempotentHint=True,
    openWorldHint=False,
)

Annotations describe expected behavior to the host. They are hints, not access controls. Here the actual restriction comes from publishing only two tools, routing them through a fixed GET endpoint, and omitting write/sync handlers. readOnlyHint marks a read, destructiveHint=False indicates no destructive effect, and openWorldHint=False describes the bounded local data source. An idempotent read can still return newer data after a sync.

Actual registration excerpt · inside create_server()
server.tool(name="get_team_dashboard", description=description, annotations=READ_ONLY)(dashboard)
server.tool(
    name="show_teambeacon_dashboard",
    title="Show TeamBeacon dashboard",
    description="Display an interactive read-only TeamBeacon dashboard. " + description,
    annotations=READ_ONLY,
    meta={"ui": {"resourceUri": UI_URI}},
)(dashboard)

@server.resource(
    UI_URI,
    mime_type="text/html;profile=mcp-app",
    title="TeamBeacon dashboard",
    meta={"ui": {"prefersBorder": True, "csp": {"connectDomains": [], "resourceDomains": []}}},
)
def dashboard_ui() -> str:
    if not UI_PATH.is_file():
        raise ValueError("Dashboard UI is not built. Run: cd app && npm run build:mcp")
    return UI_PATH.read_text(encoding="utf-8")

Reading the UI descriptor: a URI identifies the resource; its MIME type tells the host what format it contains. Here text/html;profile=mcp-app means HTML intended for the MCP Apps bridge. CSP means Content Security Policy: the resource declares which external connections and assets it expects the host to allow.

The Python SDK argument meta is serialized as _meta in the tool descriptor. UI_URI is ui://teambeacon/dashboard/v1.html, and UI_PATH points to the generated HTML file. A ui:// URI is an MCP identifier, not a browser URL and not a file path.

ResourceContentWhy it exists
teambeacon://workspaceJSONWorkspace name, read-only capability, timezone, web UI URL.
teambeacon://metric-definitionsMarkdownExplains time windows, WIP, overlapping scope, and freshness.
ui://teambeacon/dashboard/v1.htmltext/html;profile=mcp-appThe widget HTML, styles, and JavaScript.

One resource rule matters for interpretation: shared epics can occur in multiple streams. Adding all stream counts does not necessarily produce a unique team total.

Start the process over stdio

services/mcp/__main__.py
from services.mcp.server import create_server


def main() -> None:
    create_server().run(transport="stdio")


if __name__ == "__main__":
    main()

The host launches this process and exchanges MCP messages over its standard streams. Keep diagnostic output on stderr; ordinary stdout logging can corrupt the protocol stream. The Python SDK handles message framing and the core lifecycle.

CHAPTER 06

Follow a request from chat to facts

The following is the core connection flow used by the pinned Python SDK. The host has already received your request, “Show the TeamBeacon dashboard.” The SDK first establishes the connection, then the host discovers and calls the tool.

JSON-RPC is a request/response format. An id connects a response to its request. A notification has no request ID and expects no response. The host—not the model itself—transports these messages.

Illustrative core MCP request
{
  "jsonrpc": "2.0",
  "id": 7,
  "method": "tools/call",
  "params": {
    "name": "show_teambeacon_dashboard",
    "arguments": {"flow_weeks": 4, "timezone": "Australia/Melbourne"}
  }
}

The server’s callable function sees validated arguments; it does not need to parse the English sentence. If the API is offline, the tool reports an error. If one API section fails, the envelope can still carry healthy sections with an errors map.

Reference: MCP 2025-11-25 lifecycle. Newer protocol revisions can change discovery; do not mix lifecycle examples across versions.

CHAPTER 07

Add the app: HTML plus a host bridge

The render tool’s metadata lets an MCP Apps-capable host locate the UI resource. The host reads it, mounts it in a sandboxed frame, and supplies the tool result through the bridge. React is a choice made by this project; the protocol does not require React.

The bridge is the widget’s connection

In bridge.ts, requests go to window.parent.postMessage() with a JSON-RPC ID. A map tracks pending requests and a 35-second timeout. Incoming messages must come from the parent; the bridge pins a non-opaque host origin after a valid response and rejects mismatched origins. An opaque parent origin retains the source-window check.

Bridge excerpt · not a complete standalone bridge
// Excerpt: once request(), notify(), and receive() are defined.
const host = await request("ui/initialize", {
  appInfo: { name: "TeamBeacon dashboard", version: "1.0.0" },
  appCapabilities: {}, protocolVersion: "2026-01-26",
});
if (host?.protocolVersion !== "2026-01-26") {
  throw new Error("The host uses an unsupported MCP Apps protocol.");
}
notify("ui/notifications/initialized", {});

// A period change uses the data tool through the parent host.
return readDashboard(await request("tools/call", {
  name: "get_team_dashboard", arguments: filters,
}));

The widget subscribes to ui/notifications/tool-result. “Update view” and period buttons call the read tool; the work-stream dropdown filters rows locally. Link opening uses ui/open-link. Resize messages use the body’s measured height so the frame can shrink as well as grow.

A generation counter prevents a slow refresh from overwriting newer data supplied by the host. Failures leave the last successful view visible with an explanation. Unmounting removes message listeners, disconnects the observer, and rejects pending requests.

No localhost fetch from inside the widget

The widget calls its parent host. The Python adapter calls the local API. This avoids assuming that a sandboxed iframe shares the developer’s browser origin, network access, or credentials. The UI resource requests no external connection or asset domains; the host enforces its own CSP and sandbox policy.

This project implemented a small bridge directly after an npm registry certificate problem blocked the optional UI SDK installation. Certificate validation was not disabled. For a new project, evaluate the official MCP Apps SDK for the host capabilities you need. A narrow custom bridge needs explicit compatibility tests; it is not a complete implementation of every MCP Apps feature.

Build a small interface for the conversation

The main SPA keeps its existing routes. The widget has its own entry point and stylesheet under app/src/mcp/, while reusing the repository’s React, TypeScript, Vite, and test tooling.

app/vite.mcp.config.ts
import react from "@vitejs/plugin-react";
import { defineConfig } from "vite";

export default defineConfig({
  plugins: [react()],
  define: { "process.env.NODE_ENV": JSON.stringify("production") },
  build: {
    outDir: "mcp-build",
    emptyOutDir: true,
    lib: { entry: "src/mcp/main.tsx", name: "TeamBeaconDashboard", formats: ["iife"], fileName: () => "dashboard.js" },

iife makes a script that executes directly in the resource. The packager embeds the emitted JavaScript and CSS into one document, escaping closing script tags. The output is services/mcp/ui/dashboard.html; it is generated and ignored by Git.

Rebuild after every widget change

How the design evolved

  1. Prove the connection. Start with dashboard facts and a richer UI containing metric cards and issue details.
  2. Fit the host. Replace large cards with compact work-stream rows; tighten spacing and make the layout reflow.
  3. Remove duplication. Keep progress, flow, filters, and freshness. Remove highlight cards, issue lists, and cycle-time configuration text from the widget.
  4. Keep the contract. Chat still receives the richer result. Only list-limit notices for the now-hidden issue lists are suppressed in the visual view; relevant warnings remain.

Run and register the integration

Use this recipe with the implementation present in your checkout. It does not scaffold a new project. Prerequisites: Python 3.11+, Node 22.12+ as required by app/package.json, npm, and a configured Codex installation. These commands target macOS/Linux shells; Windows paths and virtual-environment executables differ.

1. Install the optional adapter and build the widget

Repository setup
# Run from your TeamBeacon checkout.
python3.11 -m venv .venv-mcp
.venv-mcp/bin/python -m pip install -r services/mcp/requirements.lock
cd app
npm ci
npm run build:mcp
cd ..

2. Keep the existing application API running

If TeamBeacon is already running, reuse it. If you only need the API, launch it from the repository root in a separate terminal:

API-only startup
python3.11 -m services.api.server --host localhost --port 8000

For a configured checkout’s full development experience, cd app && npm run dev starts both API and Vite. That script stops existing listeners on ports 8000 and 5174, so do not run it over an existing session you want to preserve. The built widget needs the API, not Vite; the “Open TeamBeacon” link needs the web app.

After applying the checkpoint-freshness change, restart an old API process once. You can verify the API independently:

Read-only API check

CHAPTER 10

Explore what changes when you click

This small teaching aid traces three actions through the implementation. It uses no network and does not execute the commands shown in this guide.

  1. Host calls show_teambeacon_dashboard.
  2. Adapter requests the existing dashboard API.
  3. Host reads the HTML resource and initializes the widget.
  4. Widget renders the supplied tool result.

A supporting host provides the UI; the model does not generate its markup.

Why this distinction matters

A period change needs a new calculation, so it traverses the host, MCP server, and API. A work-stream selection only narrows the already-returned rows, so it stays in React state. Neither action launches ingestion. The host may apply its own permission rules to a widget-triggered tool call.

CHAPTER 11

Move to another host deliberately

The reusable pieces are the typed tools, resource URIs, HTML bundle, and bridge behavior. Installation format, transport support, policies, and visual rendering differ between hosts. MCP support by itself does not imply MCP Apps support.

EnvironmentWhat this checkout can provideWhat to verify
Local host with stdio toolsDashboard facts and contextual resources, subject to host support.Executable path, environment, initialization, tool discovery and calls.
Local host with MCP AppsThe same tools plus a rendered widget.HTML resource reading, UI handshake, result delivery, filter calls, resizing, and links.
Remote/cloud agentRequires a reachable MCP deployment or an explicitly supported local bridge.Transport, authentication, authorization, network boundary, API reachability, and UI capability.
“localhost” belongs to the machine running the process

A cloud process connecting to 127.0.0.1 reaches itself, not your laptop. Setting the current configuration’s URL to a public address is also rejected by the adapter. A remote deployment is a separate design change, not a port-number edit.

A compatibility decision flow

  1. Can the host launch or reach the MCP server?No → fix command, transport, or network configuration.
  2. Can it discover and call the read tool?No → investigate initialization, schema, or API errors.
  3. Can it render MCP Apps resources?No → keep text answers and an ordinary web-app link.
  4. Do bridge initialization and filter calls work?Yes → validate resize, errors, links, and data freshness before calling it supported.

A future Streamable HTTP adapter would expose an MCP protocol endpoint, distinct from the existing REST API. Before sharing it, design identity, per-user authorization, TLS, origin validation, and access to the backing API. This checkout implements local stdio only.

Evidence from this journey: Codex discovered and called the tools, the actual stdio path returned live data, and a local browser test host rendered the widget and its compact revisions. These observations alone do not establish native UI rendering in every Codex version or other agent host. Record a successful native-host check separately.

CHAPTER 12

Test the boundaries, not just the happy path

The most useful test is a real protocol round trip: launch the stdio process with the official client, connect it to a fixture-backed HTTP API, call both tools, validate the output schema, and read the UI resource. This catches problems that a mocked Python function call would miss.

LayerWhat the tests establish
Python unitInput bounds, URL rules, response-size limits, sanitized failures, metadata, and resource behavior.
Protocol integrationInitialization, discovery, valid/invalid tool calls, data/render parity, resource reads, and absence of a sync tool.
React + bridgeRendering, filters, timeouts, parent/origin checks, unsafe links, stale responses, resize shrinking, errors, and removed visual sections.
API regressionFreshness leaves running checkpoints unchanged; tests also cover request validation, cache invalidation, cursor precedence, and interrupted-run recovery.
Host smoke testThe real host displays the widget and successfully executes one permitted UI read.

Read-only does not mean “no trust boundary”

  • The adapter reads existing API results; it does not load connector PATs or query SQLite directly.
  • Fixed loopback origins, disabled redirects, and disabled environment proxies constrain the adapter’s HTTP route. They do not authenticate every local process.
  • Source text is data, not an instruction to the agent. React renders names as text, and external links are checked.
  • Results passed to the agent can enter its model context. Local storage does not imply that all returned facts remain on the machine.
  • Tool hints and UI sandbox metadata complement implementation controls; neither substitutes for authorization.

Check your understanding

Does an MCP server need its own HTTP port?

No. This server runs over stdio as a local child process. It uses HTTP only as a client of TeamBeacon’s existing API.

Does an MCP-compatible agent automatically support this widget?

No. It also needs MCP Apps resource rendering and the relevant bridge capabilities. Keep the data tools independently useful.

Does “Update view” make the source data current?

It re-reads analytics, potentially from cache. It does not sync JIRA. Use the source-freshness timestamp to interpret the result.

Can a resource URI be pasted into a normal browser?

The custom ui:// identifier is resolved through MCP resource reads. “Open TeamBeacon” is a separate ordinary HTTP URL.

CHAPTER 14

Take the pattern to your own application

  1. Pick one useful read. Find an API operation that answers a real user question.
  2. Define the boundary. Specify inputs, output limits, freshness, failures, and authorization before adding tools.
  3. Wrap and verify. Use an MCP SDK, publish the tool schema, and test a real client round trip.
  4. Add context where needed. Publish resources for metric definitions or workspace meaning.
  5. Add UI only when useful. Register a small HTML resource and render authoritative data through the host bridge.
  6. Test the target host. Check transport and UI separately; then refine the view for the conversation.
